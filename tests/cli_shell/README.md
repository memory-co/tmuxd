# cli_shell — 命令行:每条命令就是一次库调用

## 这个场景在测什么

CLI 是第三层壳,而它和 SDK 那条链路有一处根本不同:**它必须有一个 server 在跑**。
`tmuxd ls` 活几十毫秒就退出,持不住 ttyd 也持不住状态,只能去问一个持得住的东西。
所以这里要锁的不是“功能对不对”(那在各自的场景里已经锁过了),而是**壳本身**的几件事:

0. **没起 server 时如实说**,而不是顺手起一个门面又立刻带走它 ——
   一条只读命令不该留下副作用。而且报的是**管控口**不是 ttyd 口,
   不然人会去查错的那个端口。

1. **一个 id 只有一个规范名字**:`-s` / `--id` 是规范写法(`-s` 选哪个、`--id` 说按什么认),
   `-t` / `--session` / `--target` 是 1.0.0 的拼法,**必须继续能用但不出现在 `--help` 里**
   —— 已经发到 PyPI 的参数名删不得,而规范写法要显眼。
2. **参数真的递下去了**:`-s` / `-c` / `-e` / `--` 后面的命令。
   尤其是 `--` —— `argparse.REMAINDER` 会把分隔符本身一起交回来,
   不剥掉的话 `new -s x -- cat` 实际在跑命令 `-- cat`。**这条曾经真的写错过。**
3. **退出码是接口**,不是装饰:脚本靠它判断,不该去解析输出。
   `has` 用 3 表示"不在"——那是答案不是错误。
4. **错误走 stderr**,stdout 上只有正常输出,这样 `tmuxd url -s x | xargs open` 才安全。
5. **`serve` / `start` / `stop` 是同一份逻辑套不同的壳**,而 `stop` 停的是门面 ——
   会话还在。这条在 [`survives_the_process/`](../survives_the_process/) 从库那边验过,
   这里从命令行这边再验一次,因为**用户读到的是 CLI 打印的那句话**。
6. **配置文件只是构造参数的另一种写法**,不是第二套东西。
7. **退出码 5 空着不复用** —— 它曾是“连不上远端 tmuxd”,`-H` 去掉后没有产出者。
   已经发出去的退出码不该改含义。
8. **`kill-server` 是本机动作**,不走 server:收拾残局的命令得在 server 已经挂了的
   时候还能用,而那正是你要它的时候。

## 不在这测什么

- **哪些子命令不该存在** —— 在 [`nothing_reads/`](../nothing_reads/)。
- 会话语义本身 —— 在 [`session_identity/`](../session_identity/)。
- `send` 的字面量语义 —— 在 [`typing_in/`](../typing_in/);这里只验 CLI 把文本
  原样递下去了(用的还是那句 `Enter the code`)。

## fixture 来源

- `bare`(本场景内)—— 配好实例参数(独立 `-L` 名、`--state-dir`、两个空闲端口)但
  **不起 server**,用来验“没起会怎样”;`TMUXD_CONFIG` 指向一个不存在的文件,
  免得跑测试的人自己的 `~/.tmuxd.conf` 掺进来
- `run`(本场景内)—— 在 `bare` 之上真的 spawn 一个 `tmuxd serve` 子进程。
  **就绪判断等的是一次真的 API 调用通,不是等 pid 文件出现** ——
  `status` 在只有 pid、uvicorn 还没绑上端口时就会返回 0,拿它当就绪信号
  会让用例跑在 server 起来之前(写这套时就踩了一次)
- 命令本身仍走 `cli.main(argv)` 而不是再 spawn 一个进程:壳的逻辑进程内就验得完
- `capsys`(pytest 内置)—— 抓输出
