# finding_ttyd — 三级查找,以及自带那份的代价

## 这个场景在测什么

`tmuxd = tmux + ttyd`,而 ttyd 在 Debian/Ubuntu 仓库里**根本没有**
(实测 `apt-cache policy ttyd` → `Candidate: (none)`)。所以包里自带了两个上游的静态构建
兜底。这个场景锁的是那套查找的每一级,以及它带来的义务:

1. **三级,顺序不能反**:显式 `ttyd_bin=` → PATH → 包里自带的 → 报错。
2. **PATH 优先于自带**,这是**故意的**:系统装的那个能被 `apt upgrade` 修,
   自带的只能等我们发版。自带的服务的是"系统里根本没有"那种情况,不是接管。
3. **显式指定的永不被悄悄替换。** 你点名了一个二进制,它跑不了就该报错 ——
   自动换一个会让你以为跑的是你指定的那份。
4. **PATH 上那个太旧就降级**,不是报错:记一条 warning,退到自带的。
   这条让"系统上有个老 ttyd"从故障变成无感降级 —— 也正是 PATH 优先能成立的前提。
5. **自带的那份要能真的执行。** package data 过 wheel 之后**可执行位会丢**,
   而且 site-packages 可能只读,所以要复制到状态目录再 chmod。
   这条不测就等于没实现 —— 它在开发树里"看起来能用",装完之后才炸。
6. **报错要说清下一步**:检测到什么平台、包里带了哪几个、怎么自己装,
   以及**ttyd 是必需的**(不是"少个网页入口"而已)。
7. **自带的东西是有义务的**:LICENSE 必须随包(ttyd 是 MIT),
   SHA256 得和上游对得上 —— 谁分发谁负责。
8. **清单是真相,二进制不进 git。** 每次上游发版二进制都会换,而 git 会永远留着旧的;
   值得版本化的是 `scripts/ttyd_assets.json`(版本号 + 校验和 + 架构→wheel tag)。
   所以用例验的是**清单自洽**(每个目标都有校验和、都映射到代码认得的架构、
   manylinux 与 musllinux 共用一份产物),树里恰好有二进制时再顺带验它对不对得上。

## 不在这测什么

- **ttyd 起来之后干什么** —— 在 [`the_entrance/`](../the_entrance/)。
- **同端口上已经有 ttyd 时怎么办** —— 在 [`port_reuse/`](../port_reuse/)。
- **macOS 上没有自带的** —— 这台机器是 Linux,只能断言"选择器认得平台"这一半;
  真机验证不了的事不假装验了。

## fixture 来源

- `scripts/ttyd_assets.json` —— 清单本身,发版和这些用例走的是同一份判据
- `tmp_path` / `monkeypatch`(pytest 内置)—— 造假的 PATH、假的 ttyd
- `fake_ttyd()`(本场景内)—— 写一个会打印指定版本号的 shell 脚本冒充 ttyd,
  因为要测的是**版本判定和查找顺序**,不是 ttyd 本身
