# the_entrance — 人从哪进来,以及谁进得来

## 这个场景在测什么

入口地址就是 **ttyd 原生的 `?arg=<id>`** —— 没有反向代理、没有自己发明的路径、
没有 302 跳转。少了那一跳,换来的是一条**可以直接贴给人**的地址:它不依赖任何
还活着的 Python 进程去解析。

1. **ttyd 真的在服务终端页面**,不是"端口开着就算数"。
2. **`s.url` 就是那个地址**,id 里的特殊字符百分号编码。
3. **URL 不需要活着的 Python 进程**:`start_ttyd=False` 的实例照样算得出来,
   因为它只是个字符串。
4. **token 由 ttyd 自己把关**(basic auth),没带凭据就是 401。
5. **`?arg=` 是调用方可以随便填的**,所以 pty 创建点必须再挡一道:
   `attach.sh` 只 `attach-session`,**从不创建**。填一个没建过的 id、填空、
   填一个近似的名字,都得被拒。这是"会话只能由库创建"这条不变量的最后一道闸。
6. **对外监听没给 token 就拒绝启动** —— 那是把一台机器的 shell 放到网上,
   不给"我待会再加"的机会。

## 不在这测什么

- **同一个端口上已经有 ttyd 时怎么办** —— 在 [`port_reuse/`](../port_reuse/)。
- **近似 id 为什么进不去**(前缀匹配)—— 在 [`exact_targeting/`](../exact_targeting/);
  这里只验"没建过的 id 进不去"。
- **拿到 token 的人能进这个池里的任何会话** —— 这是**已知且写进文档的**语义
  (ttyd 的鉴权是进程级的),不是缺陷,所以没有用例去"证明它不该这样"。
  要按会话授权得在 ttyd 前面套代理,那属于调用方。

## fixture 来源

- `served`(`tests/conftest.py`)—— 真起一个 ttyd 在空闲端口上
- `_attach()`(本场景内)—— 按 ttyd 调用 `attach.sh` 的方式直接跑它:
  同样的 argv、同样的 `_TMUXD_SOCK` / `_TMUXD_TMUX` 环境变量
