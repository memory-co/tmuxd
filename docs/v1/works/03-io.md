# 03 · 程序化 I/O

## 1. 这一章是 tmuxd 存在的理由

会话管理([02](02-session.md))说到底只是把 `tmux ls` 包成了 JSON。真正让 tmuxd 值得存在的是这一章:
**把 `send-keys` 和 `capture-pane` 做成从外面能调的接口。**

tmux 有这两个命令,但它们只能在那台机器的 shell 里敲。想让程序驱动一个终端会话,
今天的做法是 ssh 进去拼命令行、解析输出、自己处理转义 —— 每个人都写一遍,每个人都写歪。

| tmux 命令 | tmuxd |
| --- | --- |
| `send-keys` | `POST /api/sessions/{t}/keys` |
| `capture-pane -p` | `GET /api/sessions/{t}/capture` |
| `capture-pane -p -S -` | `GET .../capture?start=-` |
| `pipe-pane` | `WS /api/sessions/{t}/stream` |
| `resize-window` | `POST .../resize` |
| `display -p '#{...}'` | `GET /api/sessions/{t}` 的字段 |
| —(tmux 没有) | `POST .../run` —— 跑一条命令,拿输出和**退出码** |

> 这和 webmuxd 的 `/api/act` / `/api/observe` 是同一个东西的两个世界版本:
> 一个往浏览器里点、把页面读出来,一个往 pane 里敲、把屏幕读出来。
> 两边的错误码形状、幂等约定、SDK 手感都刻意保持一致。

## 2. 往里敲:`keys`

**两个字段,分得很开,这是有原因的:**

```jsonc
POST /api/sessions/work/keys
{ "text": "npm test", "enter": true }         // 字面量,一个字符都不解释

POST /api/sessions/work/keys
{ "keys": ["C-c", "q", "Enter"] }             // tmux 的按键名
```

| 字段 | 对应 tmux | 语义 |
| --- | --- | --- |
| `text` | `send-keys -l` | **字面量**,原样打进去 |
| `keys` | `send-keys` | tmux 键名(`Enter` `Escape` `C-c` `M-x` `Up`…) |
| `enter` | 追一个 `Enter` | `text` 的语法糖 |

`send-keys` 不加 `-l` 时会把参数当**键名**解析,于是 `send-keys "Enter the code"` 里的
`Enter` 变成回车键 —— 这是 tmux 用户人人踩过一次的坑。tmuxd 把它挡在 API 形状上:
**要发文本就用 `text`(默认走 `-l`),要发按键就用 `keys`,不给你混着写的机会。**

同一次请求里两个字段都给时,先 `text` 后 `keys`(所以 `{"text":"y","keys":["Enter"]}`
和 `{"text":"y","enter":true}` 等价)。

`POST` 接受 `Idempotency-Key` 头,10 分钟窗口内重放返回原结果 ——
**网络重试导致重复敲一遍命令是真实事故**,尤其当那条命令是 `terraform apply`。

### 这里没有"安全"可言,也不假装有

有人会想在这一层做命令白名单。不要做。**能 attach 这个会话的人本来就能敲任何东西**,
在 API 上拦 `rm -rf` 只会给人虚假的安全感,顺便挡住正当用法。
安全边界在 token 和网络那一层([01 §7](01-server.md)),不在这里。

同一个道理也解释了为什么 `keys` 没有只读模式、`share` 没有 `--read-only`:
**这一层全部可读可写,要锁往上层去锁**([02 §4](02-session.md))。

## 3. 读出来:`capture`

```
GET /api/sessions/work/capture?start=-&join=true&ansi=false
```

| 参数 | 对应 tmux | 默认 | 说明 |
| --- | --- | --- | --- |
| `start` | `-S` | 当前屏 | `-` = 全部 scrollback;负数 = 往回 N 行 |
| `end` | `-E` | 当前屏底 | |
| `join` | `-J` | `true` | 把被硬折行的长行接回来(见下) |
| `ansi` | `-e` | `false` | 保留颜色转义;默认输出纯文本 |

**没有选 pane 的参数** —— 一个会话就是一个终端([02 §1](02-session.md)),
`-t <session>` 交给 tmux 自己解析即可。这一节里说的"pane"一律指那个唯一的终端。

### 三个必须知道的真相

**① `capture` 给的是屏幕,不是日志。**
它抓的是 tmux 维护的那块字符网格 —— 也就是**如果此刻有人 attach,他会看见的东西**。
不是进程的 stdout。全屏程序(vim、htop、Claude Code 的 TUI)抓出来就是它当前那一屏画面,
不是它的历史输出。这是特性不是缺陷:**你要的正是"现在屏幕上是什么"。**
要连续的输出流,用 `stream`(§4)。

**② 长行会被按 pane 宽度硬折行。**

```console
# pane 宽 80 时
$ capture               →  ["…$ echo hello-$", "((1+1))", "hello-2"]
$ capture?join=true     →  ["…$ echo hello-$((1+1))", "hello-2"]
```

所以 `join` 默认开。但 `join` 只能接回**tmux 知道是折行的**那些行 ——
程序自己打的换行接不回来,也不该接。

**③ 没人 attach 时,pane 默认只有 80×24。**
纯程序驱动的会话不会有人 attach,于是所有输出都按 80 列折行,`git log --oneline` 之类
全成了面条。tmuxd 因此**建会话时就显式给尺寸**:

```bash
tmux new-session -d -s work -x 120 -y 40      # TMUXD_COLS / TMUXD_ROWS,默认 120x40
```

调用方随时可以改:

```jsonc
POST /api/sessions/work/resize   { "cols": 200, "rows": 50 }
```

> **实测(2026-08-08,tmux 3.3a)**:`new-session -d -x 160 -y 45` 在无客户端时生效;
> 150 字符的行不折;`resize-window -x/-y` 对已存在的无客户端会话同样生效,
> 且不被 `window-size latest` 覆盖(该选项只在**有客户端**时决定跟谁)。
> `capture-pane -p -J -e -S -` 四个开关可自由组合。

### 等输出:`wait_for`

```
GET /api/sessions/work/capture?wait_for=Done%20in%20&timeout=30
```

轮询屏幕直到匹配上正则(或超时 `408 timeout`),返回**匹配那一刻**的内容。
这是驱动交互式程序唯一靠谱的原语 —— 比 `sleep 3` 强,也比让调用方自己轮询省往返。

不做完整的 expect DSL。**`wait_for` 到此为止**,再往上(多步对话、分支、重试)是调用方的事。

## 4. 跑一条命令拿退出码:`run`

`capture` 回答"屏幕上是什么",但脚本真正想问的常常是另一个问题:
**"这条命令跑完了吗?成功了吗?输出是什么?"** tmux 答不上来 —— 它只有字符流,
没有"命令"这个概念。

`run` 是 tmuxd 唯一一个 tmux 里没有对应物的端点,做法是**打标记**:

```jsonc
POST /api/sessions/work/run
{ "cmd": "git rev-parse HEAD", "timeout": 30 }
```

tmuxd 实际敲进去的是:

```bash
git rev-parse HEAD; printf '\n__tmuxd_%s__%s__\n' <nonce> $?
```

然后轮询屏幕等标记出现,标记前的部分就是输出,标记里的数字就是退出码:

```jsonc
{ "exit_code": 0, "output": "9f3c1e2...", "duration_ms": 84 }
```

> **实测(2026-08-08)**:`ls /nonexistent; printf ... $?` 打进空闲 bash pane,
> `capture -S -` 里读到 `__tmuxd_r1_2__` —— 退出码 2 拿到了。方案成立。

### `run` 的前提,以及 tmuxd 怎么守它

标记法只在**pane 里正跑着一个处于提示符状态的 shell** 时有意义。
pane 里如果是 vim,这段文本会被当编辑内容插进去 —— 后果很难看。

tmux 恰好能回答"现在前台跑的是什么":`#{pane_current_command}`。所以 `run` 有一道守卫:

```
pane_current_command ∈ {bash, zsh, sh, fish, dash, ksh}   → 放行
否则                                                        → 409 not_a_shell
```

带上 `?force=true` 可以越过守卫,但那是调用方自己负责。

**守卫挡不住的两种情况,文档里要写明,不要假装能测出来:**

- shell 在提示符上**已经打了半行字**(人刚敲了一半),标记会拼在那半行后面;
- 命令跑起来后 `current_command` 变成别的,此时并发的第二个 `run` 会被守卫挡下
  —— 这恰好是想要的行为(`409 not_a_shell` 的语义此刻更接近"忙")。

对第二种,`run` 内部**按会话加串行锁**:同一会话的并发 `run` 排队,不交错;跨会话不排队。
锁的粒度就是会话,因为会话就是终端 —— 没有更细的单位了。

### `run` 不是 SSH

它不给你干净的 stdout/stderr 分离,不给你二进制安全,输出还受屏幕宽度影响。
**要跑批处理命令请用 ssh。** `run` 存在的理由只有一个:
你要在**那个特定的会话**里跑,因为那里有 tmux 现场、有环境、有别人正看着。

## 5. 流:`stream` 与录制

```
WS /api/sessions/work/stream?since=<cursor>
```

底层是 `pipe-pane -o`:tmux 把 pane 的输出复刻一份给一个外部命令,tmuxd 接住往 WS 推。

- 推的是**原始字节**(含 ANSI、含 bracketed paste 的 `ESC[?2004h/l`)。
  不做解析、不做清洗 —— 谁要渲染谁自己解;要纯文本请用 `capture`;
- `since` 给游标(字节偏移),支持断线续传;
- 一个会话只挂一份 `pipe-pane`,多个 WS 客户端共享同一份订阅。

> **实测(2026-08-08)**:`pipe-pane -o 'cat >> f'` 落下来的内容确实带
> `ESC[?2004l`、颜色码和完整提示符 —— 和 attach 到终端里看到的字节一致。

### 录制:tmux 的 scrollback 落到盘上

`TMUXD_RECORD=on` 时,tmuxd 对每个会话常开一份 `pipe-pane`,写到:

```
~/.tmuxd/records/<session>.log        # 按 TMUXD_RECORD_LIMIT 环形截断
```

这就是 tmux 的 `history-limit` 落到磁盘上的版本,也是 webmuxd"操作日志"的对应物:
**Agent 在这个会话里跑了三个小时,它到底看到了什么、干了什么,回头能翻。**

默认关。理由要写在文档显眼处:**它会把密码、token、私钥统统记到磁盘上**
—— 终端里出现敏感信息是常态,而一份 append-only 的明文日志是个真实的泄露面。
要开就自己想清楚,并且给 `records/` 上 0700。

## 6. 不做的事

- ❌ **不解析 ANSI 成结构化数据** —— `capture` 已经给了纯文本,要终端语义请在客户端跑
  xterm.js / pyte,那不是服务端该干的;
- ❌ **不做 expect DSL / 交互脚本引擎** —— `keys` + `wait_for` + `run` 是原语,
  编排是调用方的事;
- ❌ **不做输出的结构化提取**(JSON 解析、表格识别) —— 那是调用方或模型的事;
- ❌ **不做命令白名单 / 审计拦截 / 只读模式** —— 见 §2 与 [02 §4](02-session.md);
- ❌ **不做按 window/pane 的 I/O** —— 没有 window 和 pane([02 §1](02-session.md));
- ❌ **不替 shell 管环境变量** —— 要给会话注入环境就在 `POST /api/sessions` 的 `env` 里给,
  它落到 `new-session -e`;不做全局环境变量表(那是 shellbase `docs/v1/works/env.md` 干的事)。

## 7. 错误码

| code | HTTP | 意思 | 调用方该干嘛 |
| --- | --- | --- | --- |
| `no_such_session` | 404 | 会话不存在 | 先 attach 或 create |
| `not_a_shell` | 409 | `run` 的守卫拦下了 | 等,或 `force=true`,或改用 `keys` |
| `timeout` | 408 | `wait_for` / `run` 超时 | 重试或放宽条件 |
| `cmd_not_found` | 400 | URI 的 scheme 不在 PATH 里 | 改 URI 或装那个命令 |
| `name_conflict` | 409 | 派生名撞上已有会话 | 见 [02 §2.2](02-session.md) |
| `tmux_gone` | 503 | 底下的 tmux server 没了 | **告警,别重试** |
| `bad_request` | 400 | 参数不对 | 改代码 |

前三个是**调用方能自愈**的;`tmux_gone` 是这台机器出事了,该告警而不是重试。
**没有 `read_only`** —— 这一层不分权限([02 §4](02-session.md))。
SDK 里对应两个异常基类:`SessionError` 和 `ServerError` —— 和 webmuxd 的
`ActionError` / `PlatformError` 是同一个二分。
