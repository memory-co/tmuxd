# session_identity — id 说了算

## 这个场景在测什么

会话模型小到一句话:**一个 id、一个启动目录、一条启动命令**。
身份是调用方给的那个字符串,tmuxd 不解释它怎么来的。这个场景锁的是围绕 id 的几个拐点:

1. **`session()` 是"有则接上,无则创建"**(`tmux new-session -A` 的语义)。
   这是最常用的一条,也是最容易被误解成"每次都新建"的一条。
2. **id 说了算,payload 不算。** 对一个已存在的 id 再 `session(cmd=...)`,
   新给的 `cwd` / `cmd` **全部被忽略**,你接上的是原来那个现场。
   要换命令就先 `kill` 再建 —— 显式的。误以为"参数变了就会重建"会让人
   在生产上以为自己重启了服务,其实什么都没发生。
3. **`session()` 和 `get()` 是两个动词,不是一个布尔参数。**
   "我以为会接上结果开了个新的"是最难查的那类 bug,所以分开。
   `create()` 则相反:撞了就报错,给"我确信这是新东西"的场合。
4. **非法 id 拒绝,不静默改写。** 一个被悄悄改过的 id,下次就再也找不回那个现场。
5. **命令不存在不是错误码。** 会话建起来后立刻退出,`status` 是 `exited` ——
   和你在自己终端里敲错命令是同一件事,没必要为它发明一种异常。
6. `cwd` / `env` 确实传到了 tmux(不是记在 JSON 里好看的)。
7. **没有 `rename`。** id 是身份不是标签,改名会让调用方下次按同样规则算出的 id
   找不到东西 —— 正好破坏它存在的唯一理由。

## 不在这测什么

- **`work` 会不会打到 `workbench`** —— 那是目标解析,在 [`exact_targeting/`](../exact_targeting/)。
- **id 怎么算出来的** —— 那是调用方的事,tmuxd 收到的永远只是一个字符串
  (设计理由见 works/02-session.md §2.2)。
- 会话怎么销毁 —— 在 [`survives_the_process/`](../survives_the_process/),
  因为"只有 kill 销毁"讲的是生命周期归属,不是身份。
